# "Know your unknowns": 11 more pages from Thariq's gallery

Source: https://thariqs.github.io/html-effectiveness/unknowns/index.html, built from the `unknowns/` folder of [`thariqs/html-effectiveness`](https://github.com/thariqs/html-effectiveness). The files here are byte-identical to it apart from line endings.

**Licence:** © 2026 Anthropic PBC, Apache-2.0. Every page carries `<!-- Copyright 2026 Anthropic PBC · SPDX-License-Identifier: Apache-2.0 -->`, and the repo's licence is Apache-2.0; the text is in the plugin's `THIRD-PARTY-NOTICES.md`. All names, data and numbers inside the pages are fictional ("Acme"): they show a *format*, not that an agent can produce those counts honestly.

The idea behind the set: *the map is not the territory, and the gap between them is your unknowns.* Each page is a cheap way to find one before, during or after building. Every page shows its **exact prompt** at the top with a Copy button, then the artefact, and most end in something the user pastes back (a reply, a prompt, a decisions table). See `../../shared-patterns.md` § Prompt card and § 7 Reply builder.

## How to use

Recipes exist for 01, 06 and 11 (`../../recipes/22-blindspot-pass.md`, `23-interview.md`, `24-change-quiz.md`). The other eight pages have no recipe. When the user's real need matches a row below: read the row, open the page, author a new one in the same shape, with the same ending.

| # | File | Phase | The prompt (verbatim) | Ends in | Notes from reading the page |
|---|---|---|---|---|---|
| 01 | `01-blindspot-pass.html` | before | I'm adding a new SSO auth provider to Acme but I've never touched the auth module. Do a blindspot pass: find my unknown unknowns in this part of the codebase, explain each one, and tell me how to prompt you better for the implementation. | one assembled prompt | Seven typed cards (landmine / convention / missing concept), each with "why it bites" and its own copyable prompt chip; opens with "what you asked for vs what you're actually walking into" |
| 02 | `02-color-grading-explainer.html` | before | I don't know what color grading is but I need to grade the Acme launch video. Teach me color grading well enough that I understand my unknown unknowns and can prompt you with real vocabulary. | prompts using the new vocabulary | Vocabulary ladder, a live frame with sliders and three presets; closes with "Prompts you couldn't have written an hour ago" |
| 03 | `03-design-directions.html` | before | “I want a review-queue dashboard for Acme but I have no visual taste and don't know what's possible. Make me one HTML page with 4 wildly different design directions so I can react to them.” | a reply (pick + steal/skip) | Same dataset in four philosophies, so only the design varies; reply is preselected so it is never empty |
| 04 | `04-toolbar-mock.html` | before | Before wiring anything up, make a single HTML file mocking Acme's new frame-annotation toolbar with fake data. I want to react to the layout before you touch the real app. | a reply template | Three toggleable placements, then four "layout calls I'd rather not guess" with options |
| 05 | `05-churn-brainstorm.html` | before | Here's my rough problem: Acme users churn after onboarding. Search the codebase and brainstorm 10 places we could intervene, from cheapest to most ambitious. I'll tell you which ones resonate. | a reply (ticked numbers) | Ten options on a cost spectrum; Copy disabled until something is ticked |
| 06 | `06-interview.html` | before | Interview me one question at a time about anything still ambiguous in the annotation-export feature. Prioritize questions where my answer would change the architecture. | decisions table + follow-up prompt | Seven questions, one at a time, tagged by blast radius (architecture / data model / UX / polish), options with trade-offs, free-text "Other" |
| 07 | `07-reference-port.html` | before | This Rust crate in vendor/rate-limiter implements the exact backoff behavior I want. Read it and reimplement the same semantics in our TypeScript API client — but first show me a semantics map so I can confirm you understood it. | "semantics confirmed" or a correction template | Matched code excerpts, gotchas, edge-case tables; "nothing gets implemented until you sign off on this page" |
| 08 | `08-implementation-plan.html` | before | Write an implementation plan for annotation export as HTML, but lead with the decisions I'm most likely to tweak: data model changes, new type interfaces, and anything user-facing. Bury the mechanical refactoring at the bottom — I trust you on that part. | "tweak these three things" | Sorted by likelihood of being tweaked, not by execution order; toggle to compare an alternative |
| 09 | `09-implementation-notes.html` | during | “Keep an implementation-notes file as you build the export feature. If you hit an edge case that forces you to deviate from the plan, pick the conservative option, log it under ‘Deviations’, and keep going.” | bullets for attempt #2 | The frame names a `.md` file: **the log is markdown, this page is its read view**. Filters: all / deviations / for you |
| 10 | `10-pitch-doc.html` | after | “Package the prototype, the spec, and the implementation notes into a single doc I can drop in Slack to get buy-in on shipping annotation export. Lead with the demo.” | sign-offs | Leads with a replayable demo, pre-answers reviewer objections with evidence, names who signs off on what |
| 11 | `11-change-quiz.html` | after | I want to make sure I understand everything that happened in this change before I merge. Give me an HTML report on the export-feature diff — context, intuition, what was done — with a quiz at the bottom that I must pass. | pass / "re-read these sections" | Six scenario questions about *consequences*, not recall; pass needs 6 of 6; a miss quotes the section and the fail screen links its anchors |
